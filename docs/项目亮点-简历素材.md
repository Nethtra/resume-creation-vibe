## 3. 亮点深挖（面试展开讲的核心弹药）

### 3.1 真文本层 PDF —— 产品的差异化根基

- **行业痛点**：主流工具（含不少商业站）用 html2canvas 把页面画成图片再包进 PDF——人看着没问题，ATS 机器解析时一个字都读不出来。
- **技术方案**：`@react-pdf/renderer` 用 React 组件描述排版 → 生成矢量真文本 PDF；注册 OFL 开源中文字体（Noto Sans/Serif SC、霞鹜文楷、朱雀仿宋、资源圆体）保证中文嵌入。
- **难点**：预览是 HTML、导出是 PDF，两套渲染引擎。解法 = 同一数据源 + 统一布局基准（预览 794px ↔ PDF 595.28pt，系数换算）+ E2E 断言产物文本与预览一致。
- **数字**：6 套模板 × 9 主题色 × 5 字体 × 11 档字号 × 7 档行距 × 5 维间距，全部参数同步进 PDF。

### 3.2 中文字体子集化 —— 体积工程的完整闭环

- **问题**：中文字体全量约 10MB/字重，5 族 × 3 字重根本没法直接进网页。
- **方案**：写构建脚本（`subset-font`）在构建期按「GB2312 全集 + 姓名补充生僻字 + ASCII = 8318 码点」子集化出 13 个文件（约 38MB 总库）；运行时只按当前字体族懒加载 2~7MB。
- **细节加分项**：①导出前比对构建期生成的字形覆盖清单（charset.json），超出字库的生僻字如实 toast 提示（不静默烂掉）；②Font.register 前先 HEAD 预检字体可达性——fontkit 解析 404 响应体会**硬崩且无法 try/catch**，必须提前拦截。

### 3.3 PNG 导出方案演进 —— 一段完美的「踩坑-决策」故事

1. 首选 DOM 截图（modern-screenshot）：开发环境完美，**构建产物下 foreignObject 无法可靠嵌入 webfont**，回退字体度量差导致文字重叠——实测否决；
2. 终案：把刚生成的 PDF 用 pdf.js 按页光栅化、纵向拼接成长图——与 PDF **同源渲染，一致性 100%**，2 倍清晰度，多页自动拼接，canvas 16000px 上限自动降倍率。
- **面试点**：技术选型不迷信库的宣传，用「构建产物」这个真实环境验证；失败方案的数据（为什么失败）比成功方案更值钱。

### 3.4 三层自动化验证体系

- **Node 端 E2E**：esbuild 把真实 React 组件打进 Node 渲染，pypdf 解析导出的 PDF 断言——文本层可提取、阅读顺序正确、A4 尺寸精确、字体已嵌入；模板 × 字体 × 排版参数循环覆盖。
- **浏览器自动化**：真实交互链路（填写→预览→模板切换→导出下载），含移动端 375px 视口。
- **Lighthouse 门禁**：性能 98 / 无障碍 100 / 最佳实践 100 / SEO 100。
- **支撑节奏**：6 轮「实测反馈 → 逐条落地 → 自动化验证」，用户级验收问题（假字号、轮播截断、侧栏未拉满）全部被抓住并清零。

### 3.5 零后端隐私架构 —— 产品决策 + 工程实现一体

- **产品侧**：竞品全靠「账号 + 云端 + 导出收费」变现，「真免费 + 本地隐私」是空位，也是卖点。
- **工程侧**：zustand persist 一行配置自动保存 localStorage；**版本号 + migrate 做字段级数据迁移**（v1→v5，老用户升级不丢数据）；JSON 导入导出给数据自主权；断网可用。
- **可验证**：F12 Network 面板零第三方请求——隐私不是口号，是可以当场面验的。
- **诚实代价**（面试官若追问）：换设备不同步，用 JSON 备份缓解；未来若做云同步，数据模型不变，加轻后端即可。

### 3.6 SPA 的 SEO/GEO —— 纯静态站的内容可达性问题

- SPA 原始 HTML 没有正文（h1 都没有），不执行 JS 的爬虫（GPTBot、百度）抓不到任何内容；
- 解法：静态 JSON-LD 三段（WebSite / WebApplication / FAQPage，FAQ 与页面可见文案逐字一致并脚本校验）+ `<noscript>` 静态正文兜底 + robots.txt 显式放行 AI 爬虫（GEO：AI 引擎抓不到就不会引用你）+ headless 浏览器自动生成 OG 分享图；
- **结果**：Lighthouse SEO 91 → 100。

### 3.7 无障碍 100 分的具体做法

语义化标签与 aria 状态、强调色做对比度衍生（#D97757 → 文字用 #B85C3F / #A9502F 保证 ≥4.5:1）、全局 focus-visible 焦点态、`prefers-reduced-motion` 动效降级。深浅色双主题下简历纸恒定白底（「Word 深色模式」的产品隐喻）。

## 4. STAR 故事（行为面试 / 「讲个你印象最深的 bug」）

**故事 A · 双栏 PDF 侧栏背景没拉满整页**
- S/T：用户实测发现双栏模板导出的 PDF 里，侧栏浅色背景只到内容结束处，下方一段白色——商业模板必须整页贯通。
- A：我最初判断「HTML 预览纸高=内容高，所以不用修」，被用户实测纠正后定位到根因：PDF 纸张是固定 A4 高度，与 HTML「纸随内容长」的语义不同；给侧栏 row 加 `minHeight: 100%` 修复，并用像素采样验证背景色贯穿页顶至页底。
- R：教训固化为流程——视觉问题不能靠「语义推断」，要渲染成图/采样数值做用户级验收。

**故事 B · PNG 导出整条方案推倒重来**
- S/T：PNG 长图是分享刚需，首选的 DOM 截图方案开发环境一切正常。
- A：构建产物实测发现文字重叠，定位到 foreignObject 的 webfont 嵌入缺陷——这是库级限制，绕不过；果断改道「从同一次生成的 PDF 光栅化」，顺带获得与 PDF 的一致性保证。
- R：多花的半天换来方案正确性；「在真实构建环境下验证」从此成为验收前置项。

**故事 C · E2E 回归失败先查测试**
- S/T：一次模板回归跑批，dark 模板断言 FAIL，看似产品坏了。
- A：排查两轮后发现问题在测试脚本自身的用例映射（循环里模板→用例对应错了），产品代码无误。
- R：回归失败的第一反应应该是「先怀疑断言映射，再怀疑实现」——这句写进了项目踩坑记录。

## 7. 「AI 协作开发」怎么讲（2026 求职的差异化点）

你的目标岗位是 AI 应用落地——这个项目恰好是「会用 AI 做工程」的实证，讲法如下：

1. **角色分工说清楚**：AI（ZCode agent）承担编码执行；**我负责产品定义、技术选型决策（自研 vs fork、PDF 方案三选一、设计 tokens）、每轮实测验收与取舍**——AI 是结对程序员，不是甩手掌柜。
2. **流程是工程化的**：方案文档 → 决策点确认 → 小步交付（每轮可运行版本）→ 我实测抓问题（假字号、轮播截断、侧栏未拉满等 3~5 条/轮）→ 逐条落地 + 自动化验证。6 轮迭代零遗留。
3. **验收能力是护城河**：面试官担心「AI 写的你懂不懂」——用 §5 的 Q&A 证明你能讲清每个关键机制的原理和踩坑；用「我抓出了 AI 自己验收时漏掉的问题」证明人的判断不可替代。
4. **与目标岗位的连接**：这套「给 AI 定验收标准 → 让 AI 交付 → 人做质量关卡」的方法论，正是 AI 应用落地需要的核心工作方式；项目路线图里还预留了 AI 简历润色（P2）的产品位。
